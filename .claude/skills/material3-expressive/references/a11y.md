# Accessibility contract

The library owns native semantics, state, focus rings, forced-colors fallbacks,
48px minimum targets, and reduced-motion behavior. It cannot invent names,
document structure, grouping, or announcement policy — those are the app's, and
they are where nearly every accessibility defect in an M3E app lives.

## What you must supply

| Component | You must provide |
| --- | --- |
| `IconButton` | `aria-label` (children are decorative) |
| `FloatingActionButton` | `aria-label` (icon is decorative; an extended FAB's `label` is enough) |
| `Checkbox`, `Radio`, `Switch` | a visible `<label htmlFor>` or `aria-label` — none render one |
| `Radio` | `name` (required by types) so the group exists natively |
| `Slider` | label + a visible current value |
| `RangeSlider` | `startAriaLabel`, `endAriaLabel` (required) |
| `SplitButton` | `trailingLabel` (required) |
| `FabMenu` | `triggerLabel` (required) |
| `Menu` | the trigger's `aria-haspopup="menu"`, `aria-expanded`, and click wiring |
| `Dialog` | `title`, or `aria-label`/`aria-labelledby` (dev builds warn when all are missing) |
| `BottomSheet` | `aria-label` / `aria-labelledby` for the sheet pane |
| `Badge` | `label` describing the count ("3 unread messages") |
| `Carousel` items | `label` per item; `onActivate`/`href` if they are actionable |
| Progress + `LoadingIndicator` | `aria-label`, and an announcement policy for the region |
| `Icon` used to convey meaning | `decorative={false}` + `label` |
| `nav` regions (when more than one) | `aria-label` on each |
| Every screen | one `<h1>`, correct heading order, one `<main>` |

`AppBar title` is a slot, not a heading. If the bar shows the page title, render
`<Text as="h1" variant="titleLarge">` inside it — otherwise the page has no
heading.

## What you must not add

- `role="button"`, `tabIndex`, `onKeyDown` activation, or `aria-pressed` on
  library controls. They render real elements and manage their own toggle state.
- `aria-modal` or focus-trap libraries around `Dialog`/`BottomSheet` modal /
  `NavigationDrawer` modal — they use the native `<dialog>` top layer, which
  already traps focus, makes the background inert, and restores focus on close.
- A wrapping `aria-live` region around `Snackbar` — it is already `role="status"`,
  so wrapping it causes double announcements.
- `outline: none` anywhere. The focus ring is token-backed
  (`--m3e-comp-*-focus-ring-*`) and required.
- `aria-label` on a control that already has visible text — it overrides the
  visible name and breaks voice control ("click Save" stops working).

## Names and labels

- Prefer a visible `<label htmlFor>` over `aria-label`. It gives a click target,
  survives translation, and matches what users say.
- The accessible name must **start with** the visible text when both exist.
- Icon-only controls need a verb: "Delete message", not "Delete icon", not "Trash".
- `placeholder` is not a label. `SearchBar` is the one exception — its
  `placeholder` is deliberately also the accessible name unless `aria-label`
  overrides it.
- Do not put the state in the name: `aria-label="Favorite"` on a toggle, with
  `aria-pressed` carrying the state — not `aria-label="Unfavorite"`.

## Keyboard and focus

What is already native: activation with Enter/Space, `disabled` removal from the
tab order, radio group arrow keys, `Dialog` focus trap and restore, `Menu` roving
focus + typeahead + Escape, `Select` combobox with `aria-activedescendant`,
`Tabs` arrow-key movement, `FloatingToolbar` roving focus, `Tooltip`
hover/focus/Escape.

What you own:

- **Tab order follows DOM order.** Never reorder visually with CSS `order`,
  `grid-area`, or absolute positioning in a way that diverges from reading order.
- **Focus after an action**: after closing a dialog focus returns to the trigger
  (native), but after deleting a row, submitting a form, or navigating a route you
  must place focus deliberately.
- **Skip link** to `<main>` on any screen with a navigation host.
- **Focus must stay visible**: a sticky `AppBar` or bottom `NavigationBar` can
  cover the focused element inside a scrolling container (WCAG 2.2 SC 2.4.11).
  Fix with `scroll-padding-block` on the scroll container equal to the bar
  heights.
- **Nothing focusable inside** an `interactive` `Card`, a `Tooltip`, or a
  `Button`/`Chip` label.

## WCAG 2.2 criteria that bite in M3E apps

| Criterion | Where it hits |
| --- | --- |
| 2.4.11 Focus Not Obscured | sticky app bars, bottom nav bars, docked toolbars over scrolled content |
| 2.5.7 Dragging Movements | `Slider`/`RangeSlider`, `BottomSheet` drag handle, `Carousel` swipe, `ListItem draggable` reorder — every drag needs a single-pointer alternative (buttons, arrow keys, a menu action) |
| 2.5.8 Target Size (Minimum) | 24×24px absolute floor with spacing; Material's 48px already satisfies it — the risk is app-authored controls, dense icon rows, and inline text links |
| 1.4.3 / 1.4.11 Contrast | custom palettes, text over images, `on-surface-variant` on tinted containers, disabled-but-still-readable states |
| 1.4.4 / 1.4.10 Resize & Reflow | 200% text and 320px-wide reflow without loss of content or horizontal scrolling |
| 1.4.13 Content on Hover | `Tooltip` content must be dismissible and non-blocking (the library handles Escape) |
| 2.3.3 Animation from Interactions | honour `prefers-reduced-motion` in app-owned animation |
| 3.3.1 / 3.3.3 Errors | `error` on a field is not enough — always supply `supportingText` with the reason and the fix |
| 3.3.7 Redundant Entry | don't ask twice; use `autocomplete` attributes |
| 3.3.8 Accessible Authentication | no puzzles; allow paste in code and password fields |
| 4.1.3 Status Messages | async results need `role="status"` (or `alert` for errors); `Snackbar` already is one |

## Async state announcements

Progress components carry `role="progressbar"` with `aria-valuemin`/`-valuemax`/
`-valuenow` (absent when indeterminate) but **no name**. Pattern:

```tsx
<div aria-busy={loading}>
  {loading && <CircularProgress aria-label="Loading messages" />}
  <p role="status" className="sr-only">
    {loading ? 'Loading messages' : `${count} messages loaded`}
  </p>
</div>
```

Rules: one live region per async area, `role="status"` (polite) for progress and
success, `role="alert"` for failures, and never a live region that re-announces on
every keystroke.

## Reduced motion and forced colors

- The library snaps spatial transitions and stops infinite decorative motion under
  `prefers-reduced-motion: reduce` while keeping state visible. App-owned motion
  must do the same — remove the animation, keep the state change.
- Under forced colors the library defers to system colors and draws explicit focus
  outlines instead of translucent state layers. App CSS must not re-assert
  authored colors there; use `forced-colors: active` to opt out of decorative
  treatment rather than fighting it.

## Verification pass

jsdom sees none of this. In a real browser, for each screen:

1. Tab through it. Every interactive element reachable, visible ring, order
   matches reading order, no trap, nothing hidden behind a sticky bar.
2. Both color modes and forced colors.
3. 200% text zoom and a 320px-wide viewport.
4. `prefers-reduced-motion: reduce`.
5. One pass with a screen reader (VoiceOver/NVDA) over the primary flow: does every
   control announce a name, a role, and its state?
6. Automated check (axe / Lighthouse) last — it catches the mechanical failures
   the manual pass might miss, not the other way round.
